# Requirements Traceability Matrix

## 1. Purpose

This document answers one question, for every formal requirement AI Piano Tutor has: **"where is this actually addressed, and how would I check it's done?"** It maps every `PR-xx` ID (`docs/PRODUCT/PRODUCT_REQUIREMENTS.md`) and every `SEC-xx` ID (`docs/SECURITY/SECURITY_REQUIREMENTS.md`) to the architecture doc(s) that design it, the engineering contract(s) that type it, the roadmap milestone that schedules it, the test-suite doc that verifies it, and one specific, checkable acceptance criterion.

This is a **navigation tool**, not a restatement of the requirements themselves — each row's "Requirement" column is a compressed pointer back to the source, not the full requirement text. Always read the cited source document for the authoritative wording. If this document and a source document ever disagree, the source document wins; file a correction here rather than trusting this document's paraphrase.

**Methodology, stated plainly so the gaps below are legible as gaps rather than oversights:** every citation in this document was verified against the actual text of the cited source, not inferred from a filename or a plausible guess. Where a requirement has no confidently-verifiable citation for a column, that cell says so explicitly (e.g., "No dedicated test named in `docs/TESTING/`") rather than pointing at a document that merely seems related. Section 6 and Section 7 collect the resulting gaps in one place so they're visible without having to read all 140 rows.

**On open questions:** two documents tracking unresolved product/engineering decisions (`docs/OPEN_QUESTIONS.md`, `docs/DECISIONS.md`) were being authored in parallel with this one and are deliberately **not** used as a source here — this document does not cite an `OQ-##` ID anywhere. Where a requirement's traceability is affected by something unresolved, that gap is described in this document's own words (what's missing, and what it blocks), not by reference to an external tracker this document doesn't depend on.

## 2. How to Read the Tables

Each table uses these eight columns:

| Column | Meaning |
|---|---|
| **ID** | The stable requirement ID from `PRODUCT_REQUIREMENTS.md` or `SECURITY_REQUIREMENTS.md`. |
| **Requirement** | A compressed, close-wording summary — not the full requirement text. |
| **Source §** | The `docs/PRODUCT_SPEC.md` section(s) the requirement traces back to, as cited by its own source document. |
| **Architecture** | The `docs/ARCHITECTURE/` doc(s) (abbreviated, see §3) that design how this is built. |
| **Contract** | The `docs/ENGINEERING/` type/contract that shapes the data involved — usually a `TYPES_AND_CONTRACTS.md` section (abbreviated `T&C`). `—` means no dedicated data contract applies (pure UI/UX or process requirements). |
| **Milestone** | The `docs/ROADMAP/M*.md` file that schedules the work. Where a requirement's mechanism and its full test coverage land at different milestones, both are listed as `Mx → My`. |
| **Test Coverage** | The `docs/TESTING/` doc/section that verifies it. `No dedicated test named` means exactly that — checked by grep and by full reading of every `docs/TESTING/*.md` file, not assumed. |
| **Acceptance Criterion** | One specific, checkable condition — quoted verbatim from `PRODUCT_SPEC.md` §29 where one exists, otherwise from `USER_STORIES.md` or a milestone file's own AC checklist, marked accordingly. |

## 3. Abbreviations

**Architecture** (`docs/ARCHITECTURE/`): `SYS`=SYSTEM_ARCHITECTURE.md · `APP-ARCH`=APPLICATION_ARCHITECTURE.md · `MUSIC-ARCH`=MUSIC_ENGINE_ARCHITECTURE.md · `AUDIO-ARCH`=AUDIO_ARCHITECTURE.md · `AI-ARCH`=AI_ARCHITECTURE.md · `FIREBASE-ARCH`=FIREBASE_ARCHITECTURE.md · `SEC-ARCH`=SECURITY_ARCHITECTURE.md · `FLOW`=DATA_FLOW.md

## 7. MVP Requirements With No Scheduling Milestone

The task instruction that motivated this section asked for this to be verified carefully, not assumed — every claim below was checked by reading every `docs/ROADMAP/M*.md` file in full (not just grepping) and confirming the requirement's subject matter never appears in any milestone's Exact Scope, Technical Requirements, or Acceptance Criteria sections.

### 7.1 PR-PLATFORM-04 — Firestore offline persistence (confirmed, no partial credit)

**The requirement:** "Firestore's built-in offline persistence is enabled; writes made while offline queue and flush automatically on reconnect" (`PRODUCT_SPEC.md` §23, MVP-tagged).

**What exists:** a fully-specified mechanism (`enableIndexedDbPersistence`, exact banner copy "Playing offline — your progress will sync later") in `docs/ENGINEERING/ERROR_HANDLING.md` §5.2, and a named-but-unimplemented test in that same document's §8.

**What's missing:** the word "offline" (or "IndexedDb," "persistence" in this sense) does not appear anywhere in `M0_FOUNDATIONS.md` through `M5_HARDENING.md`. No milestone's Exact Scope section schedules the actual `enableIndexedDbPersistence()` call or the banner component's implementation. `PERFORMANCE_TESTING.md` §10 mentions Firestore offline persistence only in passing, as an assumption ("MVP performance testing covers Firestore's built-in offline persistence behaving reasonably") rather than a scheduled deliverable or a defined test — which if anything reinforces that every document *assumes* this exists rather than any document actually *scheduling* it.

**Practical effect:** if a team executed the M0–M5 roadmap literally, section by section, this requirement would never get built, despite being MVP-tagged and specified in enough mechanical detail to implement directly.

### 7.2 PR-PLATFORM-05 — Degraded-service banner (split finding)

**The requirement:** "A persistent, non-alarming degraded-service banner appears whenever Firestore *or* Gemini is unreachable" (`PRODUCT_SPEC.md` §10/§23, MVP-tagged).

**Gemini-unreachable half: scheduled.** `M4_GEMINI_TUTOR.md` §3 explicitly builds "the exact fallback card from `docs/AI/AI_ERROR_HANDLING.md` §5.2," and `E2E_TESTING.md` §5.3 step 4 explicitly tests banner appearance under a mocked Gemini outage. This half is fully covered.

**Firestore-unreachable half: not scheduled**, for the same reason as §7.1 above — it depends on the same never-scheduled offline-persistence mechanism. No milestone builds the Firestore-specific half of this banner, and no test (beyond the same unimplemented one named in `ERROR_HANDLING.md` §8) verifies it.

**Why this is a split finding, not a duplicate of §7.1:** the *banner component* itself may well get built once as part of the M4 Gemini-degraded work (`AI_ERROR_HANDLING.md` §12 even notes it's "a shell-level concern, rendered once in the root layout, not duplicated per screen"), so the two halves likely share UI code. But *triggering* it from a Firestore-connectivity signal — as opposed to a Gemini-call failure — has no owning milestone, which is the actual gap.
